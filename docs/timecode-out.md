# Timecode out: the Timecode fixture, the generator, Art-Net in and out

**Status:** design note of 2026-11-25, revised the same day after a review
against the code, not built. It settles B138 step 1 (`BACKLOG.md`: the
fixture, the generator clock and Art-Net out) and G26 (`feature-gaps.md`:
Art-Net timecode in), which share the packet. Steps 2 (MTC out) and 3 (LTC
out) of B138 stay as the row has them and reuse the generator of this note.
The owner's decisions are in §7.

**Research:** a web survey on 2026-11-25 of what consoles and media servers
send and read over the network (§8). Sources were read, manuals sampled.
Where §1 and the G26/G27 rows of `feature-gaps.md` differ, §1 is the newer
reading.

## 0. The design in five lines

1. **One clock, the generator**, counts `hh:mm:ss:ff` at a rate in the engine:
   from its own start (Run, Stop, Locate) or from a layer's position ("video
   is master"). It is a timecode source like LTC and MTC: with Source
   **Generator** the layers chase it and the cues fire from it, so a show
   runs with no external timecode at all.
2. **A Timecode fixture runs it from the console**: Control, Hours, Minutes,
   Seconds, Frames, Rate, Source, in the channel map and the GDTF like the
   Master, and like the Master it exists without a patch (DESIGN §6.6
   decision 1), so the UI, OSC and cues reach the same parameters
   (`fixture.set`) and a cue can start the clock.
3. **Art-Net out** sends the generator's time as `ArtTimeCode` once per
   frame, 19 bytes, broadcast on an interface or to one address, from a
   thread of its own (`SyncSender`'s pattern). A machine setting, on the
   System screen.
4. **Art-Net in** is a fourth source, **Art-Net**: the same packet from a
   console (MagicQ, Pixera; a grandMA3 cannot send it) feeds the existing
   `TimecodeClock`, stream id selectable.
5. **Nothing moves on the hot paths** but one store per tick: the layer a
   generator follows publishes its position into a slot the generator
   thread reads, and the fixture's values travel in one atomic word
   (ADR-0002).

sACN carries no timecode. MTC over network MIDI (RTP-MIDI) and LTC over

worth building both ways is `ArtTimeCode`; the receiver that needs it and

MagicQ (out).

## 2. The Timecode fixture (8 channels, one per Mac)

A mode of the `machine` kind like the Master (`FixtureMode.timecode`,
`FixtureRef.timecode`, `per: .machine`, footprint 8, channel 8 reserved),
in the existence set of `ProjectDocument.fixtures` next to the Master, so
it has a resolver from the first start and `fixture.set`, OSC and cues reach
it with or without a patch (DESIGN §6.6 decision 1: a patch is only the
console address). It is **optional** like Keystone: the Patch screen does
not flag it as unplaced.

| Ch | Parameter | Bits | Default raw | Values |
|---|---|---|---|---|
| 1 | Control | 8 | 0 | bands of 64 (0–255 exactly): **Stop** 0–63 holds the time; **Run** 64–127 counts; **Locate** 128–191 sets the clock to channels 2–5 and holds it there, following the fields while they change; **Locate and run** 192–255 sets it and counts |
| 2 | Hours | 8 | 1 | `.index(max: 23)`; the generator clamps a raw value above 23 to 23 (`physical(fromRaw:)` does not clamp) |
| 3 | Minutes | 8 | 0 | `.index(max: 59)`, clamped by the generator the same way |
| 4 | Seconds | 8 | 0 | `.index(max: 59)`, clamped |
| 5 | Frames | 8 | 0 | `.index(max: 29)`; the generator clamps to one below the rate, and at 29.97 DF reads a skipped number as the next valid one |
| 6 | Rate | 8 | 51 (25) | explicit bands, as `syncBands` writes them: 0–50 **24**, 51–101 **25**, 102–152 **29.97 DF**, 153–203 **29.97 NDF**, 204–255 **30** (the last band runs to 255, so no raw value falls back) |
| 7 | Source | 8 | 0 | bands of 7: **Internal** 0–6, **Layer 1** 7–13 … **Layer 32** 224–230; 231–255 take the fallback, Internal |
| 8 | reserved | | | |

- Locate is a level, not an edge: while Control reads Locate the clock is
  the fields, so a desk programs a locate by setting the fields and the band
  in one cue and starts the clock with the next (Run, or Locate and run in
  one go). A desk that changes the fields while running changes nothing.
- Source **Layer n**: the clock is the fields plus the layer's clip time
  (`position / fps` of the clip playing, whatever the speed: at speed 2 the
  timecode advances two frames per frame, in reverse it runs backwards and
  a receiver treats that as a locate every frame, at a loop it jumps back
  to the fields and the receiver re-arms). It stands while the layer has no
  clip or is paused and moves with scrubs and jumps; Control is ignored.
  The fields are then the timecode of the clip's first frame, usually
  01:00:00:00. A sync slave's clip time is the master's, so the slave
  machine's generator is the master's time too.
- Nothing driving it (no patch, no `fixture.set`): the defaults, stopped at
  01:00:00:00, 25 fps, Internal.
- OSC: `/fanous/timecode/<key>` (`control`, `hours`, `minutes`, `seconds`,
  `frames`, `rate`, `source`), the address shape of every mode
  (`/fanous/<mode>/<key>`, `OSCAddressMap.address`); `/fanous/timecode/enable`
  keeps its meaning since no key is `enable`. `OSCAddressMap.command` gets
  the `.timecode` fixture. The GDTF gets the mode "Timecode (8ch)" with
  attributes of its own (`GDTFExporter.attribute(for:)`: a name per
  parameter, `Control2` for Control, time fields as `Position`-group
  attributes or plain names, settled in step 2) and the FixtureType
  description names the mode; both are changes to the GDTF file (§4).

## 3. The generator

`TimecodeGenerator` in `FanousEngine/ShowControl`: a `Thread` of its own
(`org.fanous.timecode.generate`, `userInteractive`, like `SyncSender`) that
sleeps with `mach_wait_until` to every frame boundary of its rate on the
host clock (`PacedThread`'s clock, `Drivers.swift`) and produces one
`Timecode` per frame. The target is a wake within 1 ms of the boundary; a
receiver's lock window is a frame and a half (`TimecodeClock`), so a
millisecond is invisible.

- **Input, from DMX and from the UI:** wherever the Master's values are
  read into the render snapshot (`ParameterSnapshotSlot.from`, in
  `DMXStore.publish`, which runs for console and internal values alike;
  not `DMXStore.tick`, the half-second housekeeping timer), the Timecode
  fixture's seven physical values are packed into one `Atomic<UInt64>`
  (seven bytes: control band, h, m, s, f, rate band, source band) the
  generator reads at each frame. No lock on the DMX path (ADR-0002); a
  change takes effect at the next frame.
- **Internal, counting:** the frame is `origin + floor((now − startHost) ×
  rate)` from the host time of the last Run or Locate, so the clock never
  drifts from the Mac's clock, as `TimecodeClock.extrapolate` counts.
  Frame counts wrap at a day as `Timecode(frameCount:)` does. Drop frame
  follows the same arithmetic as the readout.
- **Layer source:** the compositor writes, once per tick for the one layer
  index the generator asked for (an atomic `Int`, −1 for none), the layer's
  position, fps, rate (the moving flag of `publishMaster`) and the tick's
  host time into a `TripleBuffer` slot, as `publishMaster` does for sync
  masters; one store, no allocation, no lock. The generator extrapolates
  from that slot at each frame, so a rendered frame and the time sent for
  it agree within a tick.
- **Output:** every frame goes to (a) the project's `TimecodeClock` when
  `project.timecode.source` is **Generator** (`clock.update(time, at:
  frameHostTime, source: "Generator", everyFrames: 1, running:)`; Stop and
  Locate pass `running: false`, so cues fire nothing on a locate and the
  readout stands, as #467 and #463 make MTC locates and LTC still frames
  behave; `everyFrames:` exists on main, `running:` lands with those two
  drafts, so steps 3 and 4 of §6 come after them) and (b) the Art-Net
  sender (§4) when it is enabled, whatever the project's source. The two
  are independent: a show can chase LTC from the desk and still send its
  own generator to a second desk, or chase the generator and send nothing.
- **Who starts it:** the engine, with the sync sender; it stops with the
  engine. Idle (one wake per second) while Source is not Generator and the
  sender is off. Source Generator opens no input: `applyTimecodeSettings`
  clears the clock as for any source change and points the generator at it
  (no `ltcInUse`, nothing for readiness to check); the operator's switch
  off means the generator feeds the clock nothing, as for LTC and MTC.
- **Raw strings:** `project.timecode.source` is `off | ltc | mtc |
  generator | artnet`; the clock's `source` reads `Generator` and
  `Art-Net`, as `LTC` and `MTC` read today.

## 4. On the wire: ArtTimeCode

Art-Net 4 (document revision 1.4dp, 23/10/2025, read 2026-11-25), 19 bytes:

```
u8[8] "Art-Net\0", u16 OpCode 0x9700 low byte first, u8 ProtVerHi 0, u8 ProtVerLo 14,
u8 Filler1 0, u8 StreamId (0 = the master stream), u8 Frames, u8 Seconds, u8 Minutes, u8 Hours,
u8 Type: 0 = Film 24, 1 = EBU 25, 2 = DF 29.97, 3 = SMPTE 30
```

- **Encode and parse in `FanousCore/DMX/ArtNet.swift`** (step 1, PR #494):
  `ArtTimeCode` with `encoded()` and a case in `ArtNet.parse` (nil before
  for every opcode but ArtPoll and ArtDmx; the receiver's `switch` gets the
  case and ignores it until step 4). Rate ↔ Type: 24 ↔ 0, 25 ↔ 1, 29.97 DF
  ↔ 2, 30 ↔ 3; **29.97 NDF is sent as 3** (the packet has no NDF type; a
  receiver reads 30 fps timing, which is what MA3 and Pixera show for an
  NDF source) and Type 3 is read as 30. Fields out of range
  (`Timecode.isValid` at the Type's rate) make `parse` throw
  `ParseError.badField`, so a bad packet never reaches the clock; the fuzz
  suite holds the packet. The sender gets an `encode(into:)` on a fixed
  19-byte buffer (`SyncPacket.encode(into:)`'s shape) in step 3, so the
  generator thread allocates nothing per frame.
- **Out (`timecodeOut` in `settings.json`, a machine setting decoded field
  by field like `sync`, with its `CodingKeys` and `problems`):** `artnet:
  { enabled: false, interface: "any", target: "broadcast", streamId: 0 }`,
  set by a `timecodeOut.set` command of the programmer role like
  `sync.set`, refused in show mode, applied live. The sender is
  `SyncSender`'s pattern on the generator's thread: one `sendto` per frame
  on a non-blocking socket to UDP 6454 (the Art-Net port; receivers listen
  nowhere else), the target the subnet broadcast of the interface or a
  unicast address with an optional port. `--no-network` sends only to a
  unicast 127.0.0.1 target that names a port other than 6454, which the
  installed engine owns (B337's rule for sync, `SyncSettings.usable`): a
  test instance never feeds the installed engine's receiver. Dropped sends
  are counted, not retried. Sent in every state while enabled: a stopped
  clock repeats its frame, which is what an LTC generator does and what
  receivers show as stopped, and an enabled sender with nothing driving
  the generator broadcasts the defaults (the switch is the user's).
- **In (`project.timecode.source` Art-Net, device = the stream id, "" for
  any):** `DMXReceivers`' Art-Net listener (UDP 6454, already open for
  ArtDmx and ArtPoll, on the DMX queue) hands an `ArtTimeCode` to the
  engine's `ArtNetTimecodeInput`, which calls `clock.update(time, at:
  receiveHostTime, source: "Art-Net", everyFrames: 1, running:)` with the
  callback's host time: Network.framework delivers with a few
  milliseconds of jitter, under the frame-and-a-half lock window at every
  rate, and MTC's words carry the same kind of time. A frame equal to the
  last one is a still frame (`running: false`), as LTC after #463. A packet
  from one of the machine's own addresses (`SystemInfo.ipv4Addresses`) is
  dropped, so a machine that sends and listens never chases itself; the
  sync peer on the same subnet chases it only when told to (Source
  Art-Net is a project setting on that machine). No permission, no device:
  readiness has nothing to check. The readout's source line reads
  `ART-NET · stream 0 · 25 fps`. With `--no-network` the receiver is not
  started (as today), so a test instance checks this path in tests only;
  the live check is the installed engine with a sender on the LAN.
- **What changes on the wire:** nothing until a setting turns it on. The
  WebSocket `live.timecode` gains `generator` (state `stopped` | `running` |
  `layer`, `value`, `rate`, `source`) and `out.artnet` (`sending`, `target`,
  `packets`, `dropped`); `project.timecode.source` accepts two more
  strings; `settings.json` gains `timecodeOut`; the GDTF gains a mode, its
  attributes and a word in the description; the channel map and the OSC
  address map gain the fixture; existing modes and addresses stay.

## 5. What the UI shows

- **Show › Timecode:** Source gains **Generator** and **Art-Net** (with a
  Stream id field in place of Device). A **Generator** group under the
  fields: the generator's readout and state, buttons **Run**, **Stop**,
  **Locate** (to the time typed next to it), a Rate select and a Source
  select (Internal, Layer 1…n), all `fixture.set` on the Timecode fixture
  as the Internal source, so the project's Who controls policy applies as
  for every fixture (Console only: the buttons are greyed, as every
  internal control is then).
- **System:** a **Timecode out** panel like Sync: Art-Net on/off, interface,
  target, stream id, and the count sent.
- **Patch:** the Timecode fixture in the Machine group, optional like
  Keystone.
- **Status bar:** unchanged; the generator shows in the Timecode item only
  through the readout when it is the source.

## 6. Build order (one PR each, after the owner's decisions)

1. **Core, the packet** (PR #494): `ArtTimeCode`, rate ↔ Type, parse and
   encode, hand-built packets in `ArtNetTests`, the fuzz suite. No
   behaviour change.
2. **Core and web, the fixture:** mode, parameters, channel map, GDTF
   attributes and description, OSC addresses, the existence set,
   `docs/channel-map.md` and `protocol.d.ts` regenerated, the Patch
   screen's mode list and `fixtureNames` (cues can target it); tests in
   `ChannelMapTests`, `GDTFTests` and `OSCTests`. The fixture resolves;
   nothing reads it.
3. **Engine, the generator and Art-Net out** (after #463 and #467): the
   thread, the atomic word in `publish`, the compositor slot, Source
   Generator, `encode(into:)`, the sender and `timecodeOut.set`, `live`
   fields, the Timecode panel group and the System panel, the guide. New
   suites go on the `--hosted` list of `scripts/test.sh`. Measured:
   `check-mallocs.sh` on the compositor, the sender thread's allocations
   under Instruments for a minute, the wake error against the host clock
   over ten minutes (p99 under 1 ms), a sync run unchanged (`SyncTests`).
4. **Engine, Art-Net in (G26)** (after #463 and #467): the receiver path,
   Source Art-Net, the own-address drop, the guide. Measured against a
   MagicQ or Pixera sender when one is at hand (row B447), hand-built
   packets and a loopback sender in tests until then.
5. **Docs:** the Show and System pictures retaken; DESIGN §15.1 as built.

Then B138 step 2, MTC out (the engine's first MIDI output, a virtual source
and a port choice, quarter frames from the same generator frames), and step
3, LTC out on an output channel of its own after the audio routing of B4 and
B76.

## 7. The owner's decisions

Proposed 2026-11-25, to be decided:

1. **A fixture drives the generator** (B138 as the owner wrote it), and it
   exists without a patch like the Master, so the UI's buttons work on a
   show without a console. Alternative: generator settings in
   `project.timecode` and the fixture on top; more code, two paths.
2. **Locate is a level** (§2), not an edge.
3. **Layer source is clip time**: the fields are the clip's first frame,
   speed, reverse and loops show in the timecode as they do in the
   picture; Control is ignored while a layer is the source.
4. **Art-Net out is a machine setting** (System screen, `settings.json`),
   not a project setting: the target is a network fact like the sync
   target.
5. **29.97 NDF goes out as Type 3** (SMPTE 30); Type 3 comes in as 30.
6. **The sender runs in every state** while enabled, repeating a stopped
   frame, the defaults included.
