# Timecode out: the Timecode fixture, the generator, Art-Net in and out

**Status:** design note of 2026-11-25, not built. It settles B138 step 1
(`BACKLOG.md`: the fixture, the generator clock and Art-Net out) and G26
(`feature-gaps.md`: Art-Net timecode in), which share the packet. Steps 2
(MTC out) and 3 (LTC out) of B138 stay as the row has them and reuse the
generator of this note. The owner's decisions are in §7.

**Research:** a web survey on 2026-11-25 of what consoles and media servers
send and read over the network (§8). Sources were read, manuals sampled.

## 0. The design in five lines

1. **One clock, the generator**, counts `hh:mm:ss:ff` at a rate in the engine:
   from its own start (Run, Stop, Locate) or from a layer's position ("video
   is master"). It is a timecode source like LTC and MTC: with Source
   **Generator** the layers chase it and the cues fire from it, so a show
   runs with no external timecode at all.
2. **A Timecode fixture runs it from the console**: Control, Hours, Minutes,
   Seconds, Frames, Rate, Source, in the channel map and the GDTF like the
   Master. The UI, OSC and cues reach the same parameters (`fixture.set`),
   so a cue can start the clock.
3. **Art-Net out** sends the generator's time as `ArtTimeCode` once per
   frame, 19 bytes, broadcast on an interface or to one address, from a
   thread of its own (`SyncSender`'s pattern). A machine setting, on the
   System screen.
4. **Art-Net in** is a fourth source, **Art-Net**: the same packet from a
   console (MagicQ, a grandMA3 cannot send it) feeds the existing
   `TimecodeClock`, stream id selectable.
5. **Nothing moves on the hot paths** but one store per tick: the layer a
   generator follows publishes its position into a slot the generator
   thread reads (ADR-0002).

## 1. What the field does over the network

| Product | Sends | Reads | Note |
|---|---|---|---|
| grandMA3 | LTC, MTC (XLR, MIDI) | LTC, MTC, Art-Net timecode (per stream id, 8 or 16 slots by version) | "ArtTimeCode cannot be generated by the grandMA3" (manual) |
| ETC Eos | nothing | LTC, MTC through Response gateways | no Art-Net timecode (ETC community, not the manual) |
| ChamSys MagicQ | Art-Net timecode, MTC, LTC | the same | the one desk that sends Art-Net timecode |
| Pixera | — | LTC (audio, Dante), MTC, Art-Net timecode (UDP 6454, stream id) | one input at a time |
| disguise | MTC (a layer) | LTC, MTC | no Art-Net timecode in the docs |
| Hippotizer | — | LTC, MTC | Sync Manager |
| Resolume | — | LTC (audio) | users ask for MTC and Art-Net timecode |
| QLab | MTC, LTC (audio) | MTC, LTC | |

sACN carries no timecode. MTC over network MIDI (RTP-MIDI) and LTC over
Dante reach Fanous today through the MTC and LTC inputs. So the one packet
worth building both ways is `ArtTimeCode`; the one receiver that needs it
and is on most riders is the grandMA3 (in), and the one sender a tech meets
is MagicQ (out).

## 2. The Timecode fixture (8 channels, one per Mac)

A mode of the `machine` kind like the Master (`FixtureMode.timecode`,
`FixtureRef.timecode`, `per: .machine`), **optional** like Keystone: a show
without it runs as today. It exists when patched; the UI, OSC and cues reach
it only then (§6.6 of DESIGN: a fixture without a resolver is reached by
nothing). To use the generator from the UI alone, patch it to any address.

| Ch | Parameter | Bits | Default | Values |
|---|---|---|---|---|
| 1 | Control | 8 | 0 | bands of 64: **Stop** 0–63 holds the time; **Run** 64–127 counts; **Locate** 128–191 sets the clock to channels 2–5 and holds it there, following the fields while they change; **Locate and run** 192–255 sets it and counts |
| 2 | Hours | 8 | 1 | 0–23, an index (a value above 23 reads 23) |
| 3 | Minutes | 8 | 0 | 0–59 |
| 4 | Seconds | 8 | 0 | 0–59 |
| 5 | Frames | 8 | 0 | 0 to one below the rate; at 29.97 DF a skipped number reads as the next valid one |
| 6 | Rate | 8 | 25 | bands of 51: 24, 25, 29.97 DF, 29.97 NDF, 30 |
| 7 | Source | 8 | 0 | bands of 7: **Internal** 0–6, **Layer 1** 7–13 … **Layer 32** 224–230, 231–255 Internal |
| 8 | reserved | | | |

- Locate is a level, not an edge: while Control reads Locate the clock is
  the fields, so a desk programs a locate by setting the fields and the band
  in one cue and starts the clock with the next (Run, or Locate and run in
  one go). A desk that changes the fields while running changes nothing.
- Source **Layer n**: the clock is the fields plus the layer's position
  (`position / fps` of the clip playing), stopped while the layer has no
  clip or is paused, moving with scrubs and jumps; Control is ignored. The
  fields are then the timecode of the clip's first frame, usually
  01:00:00:00. Where the layer is a sync slave it follows the master through
  its own clock, so the slave machine's generator is the master's time too.
- A fixture that is patched but receives nothing holds its defaults:
  stopped at 01:00:00:00, 25 fps, Internal.
- OSC: `/fanous/generator/<key>` (`control`, `hours`, `minutes`, `seconds`,
  `frames`, `rate`, `source`), under the existing `/fanous/timecode/enable`
  family's neighbour, in the generated address map. The GDTF gets the mode
  "Timecode (8ch)" with the attributes as the Master's.

## 3. The generator

`TimecodeGenerator` in `FanousEngine/ShowControl`: a `Thread` of its own
(`org.fanous.timecode.generate`, `userInteractive`, like `SyncSender`) that
wakes at every frame boundary of its rate on the host clock and produces one
`Timecode` per frame.

- **Input:** `DMXStore.tick` (the DMX queue, after the resolvers) reads the
  fixture's seven physical values and stores them in a `Mutex<Command>` the
  generator reads at each frame; a change of Control, the fields or the rate
  takes effect at the next frame. No fixture patched: the defaults.
- **Internal, counting:** the frame is `origin + floor((now − startHost) ×
  rate)` from the host time of the last Run or Locate, so the clock never
  drifts from the Mac's clock, as `TimecodeClock.extrapolate` counts.
  Frame counts wrap at a day as `Timecode(frameCount:)` does. Drop frame
  follows the same arithmetic as the readout.
- **Layer source:** the compositor writes, once per tick for the one layer
  index the generator asked for (an atomic `Int`, −1 for none), the layer's
  position, fps, rate and the tick's host time into a `TripleBuffer` slot,
  as `publishMaster` does for sync masters; one store, no allocation, no
  lock. The generator extrapolates from that slot at each frame, so a
  rendered frame and the time sent for it agree within a tick.
- **Output:** every frame goes to (a) the project's `TimecodeClock` when
  `project.timecode.source` is **Generator** (`clock.update(time, at:
  frameHostTime, source: "generator", everyFrames: 1, running:)`; Stop and
  Locate pass `running: false`, so cues fire nothing on a locate and the
  readout stands, as #467 and #463 make MTC locates and LTC still frames
  behave) and (b) the Art-Net sender (§4) when it is enabled, whatever the
  project's source. The two are independent: a show can chase LTC from the
  desk and still send its own generator to a second desk, or chase the
  generator and send nothing.
- **Where it runs:** started with the engine, stopped with it; idle (one
  wake per second) while no fixture is patched and the sender is off.

## 4. On the wire: ArtTimeCode

Art-Net 4 (document revision 1.4dp, 23/10/2025, read 2026-11-25), 19 bytes:

```
u8[8] "Art-Net\0", u16 OpCode 0x9700 low byte first, u8 ProtVerHi 0, u8 ProtVerLo 14,
u8 Filler1 0, u8 StreamId (0 = the master stream), u8 Frames, u8 Seconds, u8 Minutes, u8 Hours,
u8 Type: 0 = Film 24, 1 = EBU 25, 2 = DF 29.97, 3 = SMPTE 30
```

- **Encode and parse in `FanousCore/DMX/ArtNet.swift`:** `ArtTimeCode`
  with `encoded()` and a case in `ArtNet.parse` (today nil for every
  opcode but ArtPoll and ArtDmx; the new case changes nothing until a
  receiver asks for it). Rate ↔ Type: 24 ↔ 0, 25 ↔ 1, 29.97 DF ↔ 2, 30 ↔ 3;
  **29.97 NDF is sent as 3** (the packet has no NDF type; a receiver reads
  30 fps timing, which is what MA3 and Pixera show for an NDF source) and
  Type 3 is read as 30. Fields out of range (`Timecode.isValid` at the
  Type's rate) make `parse` throw a new `ParseError.badField`, so a bad
  packet never reaches the clock; the fuzz tests cover the new opcode.
- **Out (`TimecodeOutSettings` in `settings.json`, machine, System
  screen):** `artnet: { enabled: false, interface: "any", target:
  "broadcast", streamId: 0 }`. The sender is `SyncSender`'s pattern on the
  generator's thread: one `sendto` per frame on a non-blocking socket to UDP
  6454 (the Art-Net port; receivers listen nowhere else), the target the
  subnet broadcast of the interface or a unicast address with an optional
  port. `--no-network` sends only to a unicast 127.0.0.1 target, as sync.
  Dropped sends are counted, not retried. Sent in every state: a stopped
  clock repeats its frame, which is what an LTC generator does and what
  receivers show as stopped.
- **In (`project.timecode.source` **Art-Net**, device = the stream id,
  "" for any):** `DMXReceivers`' Art-Net listener (UDP 6454, already open
  for ArtDmx and ArtPoll) hands an `ArtTimeCode` to the engine's
  `ArtNetTimecodeInput`, which calls `clock.update(time, at:
  receiveHostTime, source: "Art-Net", everyFrames: 1, running:)`: a frame
  equal to the last one is a still frame (`running: false`), as LTC after
  #463. No permission, no device: readiness has nothing to check. The
  readout's source line reads `ART-NET · stream 0 · 25 fps`.
- **What changes on the wire:** nothing until a setting turns it on. The
  WebSocket `live.timecode` gains `generator` (state `stopped` | `running` |
  `layer`, `value`, `rate`, `source`) and `out.artnet` (`sending`, `target`,
  `packets`, `dropped`); `project.timecode.source` accepts two more
  strings; `settings.json` gains `timecodeOut`. The channel map and the
  GDTF gain a mode; existing modes and addresses stay.

## 5. What the UI shows

- **Show › Timecode:** Source gains **Generator** and **Art-Net** (with a
  Stream id field in place of Device). A **Generator** group under the
  fields, shown while the fixture is patched: the generator's readout and
  state, buttons **Run**, **Stop**, **Locate** (to the time typed next to
  it), a Rate select and a Source select (Internal, Layer 1…n), all
  `fixture.set` on the Timecode fixture as the Internal source, so the
  project's Who controls policy applies as for every fixture. Not patched:
  one line, "Patch the Timecode fixture to run the generator".
- **System:** a **Timecode out** panel like Sync: Art-Net on/off, interface,
  target, stream id, and the count sent.
- **Patch:** the Timecode fixture in the Machine group, optional like
  Keystone.
- **Status bar:** unchanged; the generator shows in the Timecode item only
  through the readout when it is the source.

## 6. Build order (one PR each, after the owner's decisions)

1. **Core, the packet:** `ArtTimeCode`, rate ↔ Type, parse and encode, hand-
   built packets in `ArtNetTests`, the fuzz suite. No behaviour change.
2. **Core and web, the fixture:** mode, parameters, channel map, GDTF, OSC
   addresses, `docs/channel-map.md` and `protocol.d.ts` regenerated, the
   Patch screen's mode list and `fixtureNames` (cues can target it). The
   fixture is patchable and its values are resolved; nothing reads them.
3. **Engine, the generator and Art-Net out:** the thread, the DMX tick
   store, the compositor slot, Source Generator, the sender and its machine
   setting, `live` fields, the Timecode panel group and the System panel,
   the guide. Measured: `check-mallocs.sh` on the compositor, the frame
   times of the sender against the host clock over ten minutes (B44's gap).
4. **Engine, Art-Net in (G26):** the receiver path, Source Art-Net, the
   guide. Measured against a MagicQ or Pixera sender when one is at hand
   (row B447), hand-built packets until then.
5. **Docs:** the Show and System pictures retaken; DESIGN §15.1 as built.

Then B138 step 2, MTC out (the engine's first MIDI output, a virtual source
and a port choice, quarter frames from the same generator frames), and step
3, LTC out on an output channel of its own after the audio routing of B4 and
B76.

## 7. The owner's decisions

Proposed 2026-11-25, to be decided:

1. **A fixture, not a settings page**, drives the generator (B138 as the
   owner wrote it); the UI's buttons are `fixture.set` on it, so it has to
   be patched to be used from the UI. Alternative: generator settings in
   `project.timecode` and the fixture optional on top; more code, two paths.
2. **Locate is a level** (§2), not an edge.
3. **Layer source: the fields are the clip's first frame**; Control is
   ignored while a layer is the source.
4. **Art-Net out is a machine setting** (System screen, `settings.json`),
   not a project setting: the target is a network fact like the sync
   target.
5. **29.97 NDF goes out as Type 3** (SMPTE 30); Type 3 comes in as 30.
6. **The sender runs in every state** while enabled, repeating a stopped
   frame.
